# 玩家绑定、社区评审与创建额度

- 版本：v0.5；更新：2026-10-03。
- 主文档：[需求基线](REQUIREMENTS.md)，主要对应 REQ-31～REQ-40。
- 状态：pilot-v1政策已在GitHub实施计划中批准；配置已落地，投稿、账本与真实奖励尚未实现或启用。

## 1. 已确认目标与未确认边界

已明确的目标是：不运营自建常驻后端；社区可以持续保存和维护赛博墓地；支持绑定 VRChat 玩家；默认提供一次创建机会，额外创建次数可以通过参与评审取得。

最新澄清已确认允许且优先依赖 GitHub；排除的是个人运营的有限服务器资源和长期服务，不是排除所有平台。静态分享、邀请入口与评审奖励都遵守此约束，见 [社区正向循环计划](../plans/COMMUNITY-LOOP.md)。允许为他人建碑，被纪念对象无需 VRChat 身份。

用户已明确：墓园是一个大家可以进入的 VRChat 世界，里面放置多位投稿者的多座墓碑。访客能浏览该墓园全部审核通过且仍公开的墓碑，不限于本人的内容；不引入每人独立世界或个人墓园层级。原有 4,096 容量继续指墓碑预留数，不是墓园世界数量。

已确认每个GitHub社区成员初始一次新建墓碑机会；VRChat绑定可选，三次独立确认的有效评审兑换一次创建。完整执行阶段见 [GitHub开发计划](../plans/GITHUB-DEVELOPMENT.md)，可机器校验的配置为config/policy.json。

将三个问题分开：

1. **墓碑关联谁**：纪念内容可关联 0～3 名玩家，不授予权限。
2. **谁在参与社区**：社区成员是投稿、评审和额度的主体，可绑定其自己的 VRChat 账号。
3. **谁有权接纳与结算**：社区规则指定的审核／发布责任人，不由玩家显示名、评论数或额度余额决定。

## 2. 无服务器与去中心化的可行边界

### 2.1 建议采用的首版解释

| 层次 | 建议达到的目标 | 不作出的承诺 |
| --- | --- | --- |
| 运行与托管 | 静态内容加按事件运行的 Actions，无自建常驻服务；允许人工审核。 | 不声称没有服务器、没有托管费用或无需维护。 |
| 数据 | 源数据、被授权保留的图片、规则与必要账本可备份和重建。 | 不保证能够删除所有人的副本。 |
| 社区 | 独立社区能够维护自己的规则、授权维护者与内容集合，并可分叉。 | 不以一个原作者为永久唯一决策者，也不宣称没有本地治理权力。 |
| 额度 | 每个社区在自己的规则和身份范围内结算。 | 不保证跨社区的“每个自然人全球只能领一次”或全球通用余额。 |
| 展示 | 世界读取事先配置的可信静态数据来源。 | 不承诺旧世界自动发现所有 Fork，或自动接管旧世界发布权限。 |

建议区分 `community_id` 与图片站点：多个图片仓库仍可以服务同一个社区，不会因为分片而增加初始创建次数。该命名空间是设计建议，不是本阶段已实现的身份基础设施。

### 2.2 镜像、接续维护与独立分叉

- 镜像复制同一社区状态，不创建新奖励事件、不重置余额。
- 接续维护沿用该社区的已接纳记录、身份历史和已消费额度，交接写入权；不能让互不协调的镜像同时消费同一余额。
- 独立分叉采用新的社区身份并明确承认哪些历史。原墓碑保留来源信息，以“来源社区＋原 ID”消除不同社区都出现 `CC-000001` 的歧义。
- 初始余额的导入须有明确政策和导入记录，不能把历史评审全部重新发奖。
- 首版建议不提供跨社区额度转移、兑换和合并；需要这类能力时另行设计可信结算机制，而不是复制余额文件。

首版额度在本社区结算，不跨Fork自动兑换、合并或回流；镜像接续保持原记录。依赖GitHub平台和独立社区规则均已在实施计划中确认。

## 3. 社区成员与 VRChat 账号绑定

### 3.1 建议的逻辑记录

| 信息 | 作用 |
| --- | --- |
| 社区内稳定成员标识 | 作为额度主体，不随昵称或绑定变化重新生成。 |
| GitHub 主体引用 | 确定由谁提交申请或评审；不只用可变的显示名称识别。 |
| VRChat 账号引用 | 指向待绑定账号的稳定个人资料引用；不使用 Udon 的实例网络 ID。 |
| 绑定状态 | 建议区分未核验声明、已核验、已撤销和待复核；不能把提交资料链接显示为认证成功。 |
| 核验与变更记录 | 记录核验方式、时间、处理角色及结论；不存储密码、Cookie、会话令牌或原始私密证据。 |

建议同一社区内一个成员只有一个有效主绑定，同一 VRChat 账号不能同时绑定到多个额度主体。解绑、换绑、GitHub 改名和账号恢复走原成员的变更流程，不自动补发初始额度；绑定唯一性不能阻止同一自然人另建多个账号。

VRChat绑定已确定为可选，领取与评审主体是GitHub数字账号ID。普通浏览不登录，投稿需GitHub账号，被纪念对象不必是玩家。

### 3.2 核验能力及候选流程

官方 Player API 提供玩家显示名，`GetPlayerId` 的语义是网络 ID；不能据此得出对持久账号的控制权证明。[Player API](https://creators.vrchat.com/worlds/udon/players/) · [Getting Players](https://creators.vrchat.com/worlds/udon/players/getting-players/)

当前未验证到可直接满足本项目的官方账号认证流程，因此不把自动 OAuth、抓取私人接口或世界内显示名匹配写作已可用方案。

POC-06 优先验证一个无需自建服务的人工挑战流程：

1. 成员从自己的 GitHub 身份提交绑定申请，声明目标 VRChat 账号。
2. 维护流程签发一次性、限时、绑定本社区／本申请／目标账号的挑战内容。
3. 若 VRChat 当前公开资料能力允许，申请者在自己可控制的资料位置临时展示挑战内容。
4. 独立核验者直接查看所声明账号的当前资料，而非仅接受截图或转述；同时核验申请来源身份。
5. 核验通过后登记绑定，挑战作废；超时、账号不符或已使用则拒绝。更换目标账号需新申请，不能重用证明。

这是候选方案，公开资料的可编辑与可见性、操作负担、期限及证明保存范围均需验证。若不可行，继续保持“未核验”，不得用同名玩家或截图自动降级通过。核验公开绑定前需征得同意，因为关联 GitHub 与 VRChat 本身可能暴露跨平台身份。

## 4. 默认一次与创建消费

### 4.1 基本规则

- 默认初始创建额度为 **1次**，主体为记录过的GitHub社区成员数字ID，不要求加入组织或绑定VRChat。
- 初始额度在本社区一次性发放，不按月刷新、不因改名、解绑重绑或撤下重新领取。
- 一次额度用于新建一座纪念条目；关联三名玩家仍只消费创建者一次，不从被关联者领取额度。
- 创建额度与内容审核、人物授权、墓位容量是三个独立条件。有额度不等于可以跳过审核、保证即时发布或保证存在空墓位。
- 建议额度不可出售、转让或兑换金钱，也不决定审核票权。对现有条目的普通编辑不消费新建额度。

### 4.2 推荐结算时点

建议使用“**接纳即结算**”，不在 Issue 创建时扣次：

```text
提交草稿 → 内容审核与构建预检 → 读取当前社区余额
                                      ↓
                       同次变更接纳条目＋消费 1 次
                                      ↓
                          部署静态内容（可重试）
```

- 草稿、被拒绝或接纳前取消的投稿不扣次，也没有“退款”。
- 在正式接纳时重新校验余额与空墓位，不能只相信 PR 初次检查的旧结果。
- 已接纳内容与消费记录作为同一次权威变更落地；不能只扣次未记内容，或只收内容未扣次。
- 部署失败保留待发布的接纳结果，仅重试部署，不重复收费；永久放弃该次接纳时通过一次可审计的更正释放额度并取消对应接纳，不能仅给余额加一。
- 只有 1 次余额的成员可以提交多份草稿，但并发接纳最多成功一份，其余等待更多额度，不允许出现负余额消费。
- 发布后的常规撤下不自动退次；维护差错走有理由的补偿记录，拒绝或接纳前取消不扣次。
- 将已发布墓碑整体换成另一个无关纪念对象，应作为新建审核，不能以“编辑”绕过额度。

## 5. 什么评审能够获得奖励

### 5.1 有效贡献，而非机械投票

建议的有效评审应指向明确的投稿及其修订版本，覆盖适用的内容、人物同意、图片权限、表达与数据完整性检查，并给出可核验的理由。使用“赞成”“修改后再审”“不建议发布”都可以成为有效贡献。

投稿最终被拒绝并不使有价值的评审失效。反过来，投稿最终获准也不意味着所有点赞和评论都能领奖。评审核验者确认的是贡献质量，不是意见是否迎合最终决策。

### 5.2 建议的参与与发奖流程

1. 具有评审资格的成员领取一个尚需评审的任务；不要求先有创建额度。
2. 成员提交结构化评审并注明利益关系，单投稿最多两个获奖任务。
3. 无利益冲突的核验者确认其有效性，并记录理由；不能批准自己的奖励。
4. 有效贡献以唯一评审标识记入账本；同一成员对同一投稿的同一评审任务，评论拆分和补充修订不产生多次奖励。
5. 达到政策规定的兑换条件后记入创建额度，重跑不重复兑换；未兑换的有效贡献不得静默丢失。

pilot-v1已确认 **3次有效评审换1次创建**；每次贡献须由无利益冲突的维护者独立确认，未兑换贡献保留。邀请、点击和转发不发奖。政策变更不得让同一历史贡献重复兑换。

### 5.3 防刷与公平性

- 自己的投稿、自己共同维护的条目、自己作为相关玩家的条目，不为自己产生评审奖励。
- 已知关联账号、串谋互刷、复制评论、拆分评论、重复任务，以及为制造评审任务而提交的垃圾内容不计奖。
- 不以双方互相审核一次就自动定性串谋；异常互动作为复核信号，需记录证据与申诉渠道。
- 单个投稿最多两个可奖励评审任务；核验者不能核验自己的贡献。当前仅一位维护者，真实奖励开启前加入第二位能够独立确认的维护者。
- 审核者可贡献但不能既生成任务又独自确认自己的贡献。初始维护者依据公布的授权履职，不需要先刷出额度才能启动社区。
- 账号绑定不能证明“一个自然人只有一个账号”；需要明确剩余风险，不承诺绝对防女巫攻击。
- 没有待审内容时，不保证每位成员立即获得额外额度；公开任务不足状态，不能鼓励制造垃圾投稿。是否扩展到其他维护贡献，留作未来范围，不擅自增加。

## 6. 额度账本与无常驻服务结算

### 6.1 权威数据与派生数据

建议把初始发放、有效评审确认／撤销、贡献兑换、创建消费和补偿更正记录为可重放事件，至少引用社区、成员、唯一操作、来源请求、适用政策和处理结论。静态余额是派生结果，不作为可由用户任意编辑的唯一事实。

基本核对关系：

```text
净额度 = 一次初始发放 + 有效兑换所得 + 授权补偿 - 创建消费 - 被撤销的已发奖励
```

有效评审次数不是未经兑换就直接加到净额度中的金额。每份贡献最多参与一次有效兑换；撤销贡献需能够追溯并更正其对应兑换。

若撤销已消费奖励导致净额度小于零，保留该差额，展示可消费额度为零，后续收益先抵差额；不得简单将账面截断为零后遗忘，也不得自动删除已发布墓碑。解绑或账号恢复同样不能抹去消费历史。

### 6.2 安全写入

- 每个社区选择一个权威接纳顺序；图片分片不各自维护一份可并发消费的总余额。
- 所有记账检查基于提交时的最新状态，保护权威分支并校验预期版本，阻止两个旧快照同时成功消费同一次额度。
- 工作流重试、重复 webhook、重复 PR、任务取消或服务器中断都不得重复发奖／扣次；请求必须有可恢复的持久标识与处理结果。
- Actions 按事件执行校验和结算，无需一直运行的自建进程。其并发控制只是一层辅助；默认等待任务可被替换，不能把内存队列或工作流是否运行过当成完整账本。[GitHub 并发控制](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)
- 普通贡献者可以提出账本更正，但不能修改自己的余额并绕过审核；PR 内容不得决定特权执行逻辑。社区维护者仍是受信任角色，Git 历史不是不可篡改区块链。
- 日常更正通过补偿记录完成；隐私泄露可按主文档紧急清理规则最小化或重写敏感材料，不能为了账本审计永久保存泄露信息。

## 7. 申诉、暂停与政策变更

绑定、贡献认定、奖励撤销和滥用处置均可申诉，由未参与争议利益的成员复核。评审奖励争议与墓碑内容争议分开处理：不能因为创建者的奖励账本被复核就自动认定其纪念内容违规。

发现刷取可暂停奖励结算或新增消费；暂停原因、处理角色和解除条件需记录，不抹去已有合法贡献。内容需要下架时仍按内容治理规则独立判断。

政策版本明确生效范围、主体、初始额度、有效评审、3:1兑换、任务上限与更正规则。政策已批准，但实现和独立核验条件未就绪时保持真实奖励关闭。变更不能让历史贡献重复兑换。

## 8. 已确认试点决策

| 编号 | 决策 | pilot-v1结果 |
| --- | --- | --- |
| DEC-01 | 初始额度单位 | 每GitHub社区成员一次新建墓碑机会，按稳定数字ID去重。 |
| DEC-02 | VRChat绑定门槛 | 可选，不要求被纪念对象拥有VRChat账号。 |
| DEC-03 | 兑换比例 | 三次独立确认有效评审兑换一次创建，不奖励邀请流量。 |
| DEC-04 | 参与与核验 | 成员参与，维护者独立确认，利益回避，单投稿最多两获奖任务；真实奖励前具备第二位独立维护者。 |
| DEC-05 | 退款 | 编辑不收费，接纳前拒绝／取消不扣，常规撤下不自动退，维护差错补偿。 |
| DEC-06 | 社区互认 | 本社区额度不交易、转让或跨Fork自动合并；镜像沿用原账本。 |

以上已随用户批准的实施计划确定。下一步按GH-05实现并执行POC-06～08和AC-13～18；不把配置值存在视作账本与奖励已经运行。
