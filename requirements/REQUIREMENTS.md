## 1. 项目目标与需求标记

赛博墓地的目标是成为一个**无自建常驻服务器、可由社区接续维护与分叉的去中心化数字墓地**，在 VRChat 中展示。社区能够提交、审核和维护纪念内容，成员可以绑定 VRChat 账号，默认获得一次创建机会，并通过有效评审贡献获得更多创建次数。

用户已明确：“无服务器”指不依赖个人运营的长期服务，优先GitHub。四公开仓库分别承接主站／内容、两个数据分片和世界源码；首版社区额度不跨Fork自动合并，App按事件授权，无常驻机器人或自建后台。

一座墓碑回答的是：

> 这里埋葬了什么。

它可以纪念人物，也可以表达一个身份、一段关系、一段记忆、一个社区、项目、事件或抽象事物的结束。墓碑不等同于死亡记录，不暗示关联玩家已经去世。

本文使用以下标记，避免把目标当作已实现能力：

- **需求（REQ）**：已确认目标与pilot-v1治理约束；配置已批准不等于功能实现，未执行验收仍按待测试标记。
- **平台限制（PLAT）**：截至核验日期的官方文档事实，附来源；SDK 或平台变化后需要复核。
- **待原型验证（POC）**：必须通过构建或实际客户端测试才能确定的技术参数与可行性结论。
- **验收场景（AC）**：未来产品验收方法，不代表已通过测试。

需求文档确定“要达到什么、不能承诺什么”；具体序列化格式、脚本语言、对象池实现和发布编排在技术设计阶段确定。

已确认的展示模型是：**一个供大家进入参观的 VRChat 墓园世界，容纳多位投稿者的多座墓碑**。不引入每人独立世界或个人墓园产品层级；每座墓碑仍支持 0～3 名相关玩家和九类纪念对象。

“看所有提交的墓碑”沿用既有审核要求，指该墓园接纳且当前为 `published` 的全部墓碑都可被访客浏览，不只展示访客本人提交的内容；不包括待审、争议、隐藏和撤下内容，也不承诺汇聚所有独立 Fork。全部可浏览不等于全部同时下载或显示，仍按区域加载。

已确认每个GitHub社区成员初始一次新建墓碑机会，VRChat绑定可选；三次独立确认的有效评审兑换一次创建。政策详情见GOVERNANCE和config/policy.json。

墓碑可以为他人建立，被纪念对象不必是 VRChat 玩家；投稿者、相关玩家和被纪念对象不是同一概念。已发布墓碑应有静态分享页，让未进入世界的人也能阅读和了解投稿方式，形成“发布—分享—新投稿—评审—再发布”的社区循环。

## 2. 已确认范围

| 编号 | 确定需求 |
| --- | --- |
| REQ-01 | 使用 GitHub 保存和协作维护数据，GitHub Actions 按事件校验、记账和构建，GitHub Pages 静态发布，VRChat Udon 运行时读取；不依赖自建常驻服务器。额度记账属于后续实现，非本次已完成能力。 |
| REQ-02 | 首版支持 PC 桌面与 PCVR，并在实际客户端验收；Quest 不属于首版承诺。 |
| REQ-03 | 投稿、修改、图片替换、举报和撤下使用 GitHub Issue／PR；普通投稿者不需要仓库写权限。世界内只浏览内容并提供操作指引，不写入 GitHub。 |
| REQ-04 | 提供共享的 VRChat 墓园世界，访客可浏览该墓园所有已发布墓碑，不限于本人投稿。采用固定分区和稳定墓位，预留 4,096 座墓碑的墓位与资源寻址容量；不同时实例化全部墓碑。 |
| REQ-05 | 每座墓碑最多关联 3 名玩家，最多包含 1 张主图、3 个玩家头像、3 张纪念图；无玩家、无图片均为合法内容。 |
| REQ-06 | 允许多个 GitHub 图片仓库与 Pages 站点；所有资源仍需可备份、Fork、Mirror 和迁移。 |

### 2.1 首版不包括

- 世界内直接投稿、上传图片、审核或其他远端写入。
- 自动获取或同步 VRChat 账号资料、头像、在线状态。
- 实时留言、点赞、献花、付费墓位和交易。
- 全局全文检索；不影响使用分区编号、墓位标识和墓碑 ID 寻找内容。
- 无限图片存储、无限扩容、无限期保存原始高清图片。
- 自动接管原作者的 GitHub 账号或 VRChat 世界。

账号绑定不属于“自动获取或同步账号资料”：它是经社区核验的成员身份关联。评审奖励是非货币的创建次数，不属于付费墓位或交易。

### 2.2 容量承诺

4,096 座是预留容量目标，不是已经验证的满载服务能力，也不是同时可见对象数。先用 100 座混合内容验证端到端体验，再以 4,096 座和每座最大图片数量验证构建、分片与客户端行为。满容量图片支持通过验证前，不对外宣称已经具备。

## 3. 墓碑内容与源数据契约

### 3.1 墓碑字段

以下为逻辑字段及最低约束，不是本阶段交付的可执行 Schema。必填要求适用于进入正式数据集的记录；Issue 草稿可由维护者补齐管理字段。

| 字段或字段组 | 必填 | 语义与约束 |
| --- | --- | --- |
| `id` | 是 | 唯一、永久稳定的墓碑 ID，沿用 `CC-000001` 形式；正式分配后不得给另一座墓碑使用。 |
| `title` | 是 | 墓碑标题，纯文本。 |
| `buried_type` | 是 | 下表九种类型之一。 |
| `buried_subject` | 是 | 描述“埋葬了什么”的纯文本，不要求是人名。 |
| `status` | 是 | `pending`、`published`、`disputed`、`hidden`、`removed` 之一。 |
| `epitaph` | 否 | 墓志铭，缺省时不显示虚构文本。 |
| `story` | 否 | 描述或故事，支持纯文本换行。 |
| `dates` | 否 | 具有含义的日期或区间，例如纪念日期、结束日期；不默认解释为生卒日期，不补造未知日期。 |
| `tags` | 否 | 内容分类标签。 |
| `links` | 否 | 相关链接及可读说明；作为内容审核，不自动作为下载地址。 |
| `players` | 否 | 0～3 名相关玩家，详见 3.3。 |
| 图片引用 | 否 | 主图、玩家头像、纪念图的独立资源引用，不在 JSON 内嵌图片。 |
| 墓位分配 | 发布前必需 | 分区与稳定墓位的关联；与墓碑 ID、下载资源槽位分别管理。 |
| 维护记录 | 正式处理时必需 | 投稿／变更来源、维护角色、审核结论与变更原因；私密证明不进入公共记录。 |
| 创建者与额度结算引用 | 新建结算时必需 | 关联社区成员及唯一创建操作，不从 `players` 数组推导创建者；已有数据的导入不得假装重新消费额度。 |

**REQ-07：内容完整性。** 九类对象都可以发布；必填字段不能为空。文字长度、标签数量、链接数量等具体上限由技术设计补齐，并在正式开放投稿前进入可执行校验规则。

**REQ-08：标识与位置。** ID、空间墓位、资源下载槽位是不同概念。编辑正文、替换图片或撤下其他墓碑，不得引起其余墓碑自动重排。墓位和 ID 的分配由维护流程校验冲突，不由投稿者单方面生效。

**REQ-09：安全展示。** 投稿文本按纯文本显示，不执行脚本、不允许任意富文本控制界面。链接显示不代表世界能够自动打开任意网页；首版只承诺可读信息与操作指引。

### 3.2 埋葬对象类型

| `buried_type` | 含义 | 示例 |
| --- | --- | --- |
| `person` | 某个人 | 这里埋葬了 Alice。 |
| `identity` | 网络身份／VRChat 身份 | 这里埋葬了我曾经使用的那个名字。 |
| `relationship` | 一段关系 | 这里埋葬了我们曾经的三人组。 |
| `memory` | 一段记忆 | 这里埋葬了 2024 年夏天的那段记忆。 |
| `community` | 一个社区 | 这里埋葬了一个已经关闭的 VRChat 社区。 |
| `project` | 项目／世界 | 这里埋葬了我们没有完成的世界。 |
| `event` | 事件或时代 | 这里埋葬了属于我们的那个时代。 |
| `concept` | 抽象事物 | 这里埋葬了一个不再相信的梦想。 |
| `other` | 其他 | 无法归入以上类型的纪念对象。 |

示例仅说明表达范围，不替代人物真实性、同意与内容审核。

### 3.3 相关玩家

**REQ-10：关联不等于身份认证或编辑授权。** 玩家可以是被纪念者、共同维护者、关系成员或共同记忆的参与者；关联关系不能证明本人身份，也不自动授予修改或发布权限。

每名玩家可以包含：

- Display Name：投稿时提供的公开展示名，不承诺持续同步。
- 公开名称：可选；原需求中的“VRChat Name”仅解释为愿意公开的名称，不要求登录用户名。
- 个人资料引用：可选，用于区分同名玩家；不依赖自动查询账号接口。
- 头像：可选，属于该玩家的一张图片资源，缺省使用通用占位。
- 关联说明：可选，用于描述与墓碑的关系，不用作权限凭据。

成员自己的 VRChat 账号绑定是另一份身份记录，不能因墓碑写了某玩家名字就判定已绑定；绑定本人账号也不代表可以替所有相关玩家同意发布。绑定状态、变更和核验边界见 [身份与评审奖励](GOVERNANCE.md)。

### 3.4 图片

**REQ-11：独立资源与受控数量。** 源图片与内容JSON分离维护，不在源JSON内嵌图片。运行时可将JSON元数据和像素共同构建成传输包以保证一致性。玩家头像每名最多一张；无玩家没有头像名额。每碑最多7张逻辑图片，不意味着7次独立下载。

**REQ-12：图片处理与预算。** 投稿和发布阶段校验格式、尺寸、文件体积、可解码性及引用有效性；发布资源可生成缩略图、压缩图或合图。处理不能擅自改变图片含义，衍生图需能追溯到源资源与审核记录。编码体积、解码内存和缓存总量分别限制，不能只检查上传文件大小。

数值预算与压缩质量通过 POC-02、POC-03 确定。原始高清图不承诺永久保存；备份对象至少覆盖正式采纳的源数据、保留的图片资源及构建所需材料。

## 4. 社区维护契约与内容治理

### 4.1 角色

| 角色 | 能力与边界 |
| --- | --- |
| 访客 | 浏览公开墓碑、阅读投稿／举报／撤下指引。 |
| 投稿者 | 提交内容、授权声明和修改请求；不能自行发布。 |
| 社区评审参与者 | 对他人的投稿提供实质性评审，合格贡献可获得创建额度；提交评审不等于有权发布或自行给自己发奖。 |
| 指定共同维护者 | 协助维护指定内容、提交修改；仍需审核，且与关联玩家字段分离。 |
| 审核者 | 检查内容、同意情况和图片权限，记录批准、拒绝或复核意见。 |
| 发布维护者 | 管理正式数据、墓位和发布；执行隐藏、撤下、恢复及紧急处理。 |

社区成员也可以提出修正，不因不是原投稿者而禁止反馈。审核与发布角色可以由同一维护者承担，但不能省略审核记录，也不能独自认定自己的评审奖励；自身或利益相关内容的审核需回避。具体独立核验人数见 DEC-04。

### 4.2 请求与处理

**REQ-13：可追溯维护入口。** 至少覆盖以下请求；默认需要 GitHub 账号，不承诺匿名写入。

| 请求 | 最低输入 | 处理与输出 |
| --- | --- | --- |
| 新墓碑 | 内容字段、图片来源、人物同意与公开传播声明 | 校验、人工审核、分配正式 ID／墓位、发布或说明拒绝原因。 |
| 修改／换图 | 墓碑 ID、拟修改内容、原因及相关授权 | 在 Issue／PR 中审核变更，合入后形成新发布版本。 |
| 举报 | 墓碑 ID 或定位信息、问题说明、可公开的依据 | 人工受理，必要时先停止展示，再记录复核结果。 |
| 撤下 | 墓碑 ID、请求原因、请求人与内容的关系 | 审核后隐藏或正式撤下，记录执行结果。 |
| 恢复 | 墓碑 ID、原处理记录、问题解决说明 | 重新审核，通过后恢复同一记录，不把原 ID 转给新内容。 |
| 绑定／变更绑定 | 社区成员、目标账号引用、可验证的控制权声明 | 核验后记录状态；不公开密码、Cookie 或私密证据，不因解绑重新发放初始额度。 |
| 评审／奖励申诉 | 投稿及其具体修订、评审依据或原奖励记录 | 独立核验贡献，按政策结算或更正，不按评论数直接发奖。 |

上传图片可通过 PR 或维护者依据 Issue 整理；Issue 附件不能未经审核就成为世界的直接下载源。GitHub 来源账号不等于经过验证的 VRChat 身份。

**REQ-14：草稿与已发布版本分离。** 新投稿处于 `pending`，可以先仅存在于 Issue／PR；拒绝投稿保留处理记录，不强制分配正式墓位。已发布墓碑的普通修改在候选变更中审核，审核期间维持原已发布版本，不直接覆盖或自动下架。

### 4.3 状态与可见性

| 状态 | 语义 | 世界与当前静态内容包 |
| --- | --- | --- |
| `pending` | 尚未通过审核 | 不发布正文或图片。 |
| `published` | 审核通过且允许公开展示 | 发布审核通过的版本。 |
| `disputed` | 维护者已受理、待复核的争议 | 暂停发布正文和对应图片。 |
| `hidden` | 暂时隐藏 | 不发布；允许复核后恢复。 |
| `removed` | 正式撤下 | 不发布；ID 不复用。 |

**REQ-15：状态变更受审核控制。** 新投稿通过审核后从 `pending` 转为 `published`。维护者受理需暂停展示的争议后进入 `disputed`；复核后可以恢复 `published`、转为 `hidden` 或 `removed`。隐藏／撤下后的恢复必须重新审核并记录原因。举报本身不是认定事实成立，也不由未受信任的用户直接修改正式状态。

**REQ-16：当前发布内容最小化。** 只发布 `published` 墓碑的批准内容及必要资源。非公开状态的正文、专属图片、旧缩略图与旧合图不能因构建遗漏继续留在受控的当前发布站点；合图需要重建。若同一图片仍有其他独立批准的用途，需复核该用途，涉及隐私或权利问题时处理所有受影响引用。这里的“不发布”不是保证公共源仓库不可读取。

**REQ-17：审计。** 正式内容、维护权限和状态变更保留 Git 历史，并关联请求、处理人、时间、原因及发布结果。世界用数据不得携带私密审核材料。

### 4.4 人物同意、隐私与撤下边界

**REQ-18：同意优先。** 可识别健在人物的关联需本人同意，包括在关系、记忆、社区等类型中间接识别出的第三方。逝者纪念由人工核验投稿依据与图片使用权限；无法确认时不发布。抽象表达不能用于绕过人物审核。

**REQ-19：内容治理。** 禁止冒充、骚扰、公开隐私、捏造死亡事实和未经授权使用图片。缺少玩家字段不代表可以豁免正文和图片中的人物审核。

**REQ-20：公开性告知与紧急处理。** 提交前明确告知公共 Issue、PR、Git 历史和图片仓库均非私密审核区，禁止提交身份证件、私人联系方式或私密授权证据。需私密核验的材料走维护者公布的受控联系渠道，未建立渠道时不得要求投稿者公开证据；核验方式与访问人员在开放投稿前落实。

正常撤下仅承诺更新当前受控发布内容，不能保证删除其他人的 Fork、Clone、截图和下载副本。GitHub 官方也明确指出，仅重写原仓库历史不能清除其他副本。[S5](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)

发生隐私泄露时先停止受控公开展示，再清理相关源文件、发布资源、衍生图与必要的历史／缓存引用，按需联系 GitHub 和镜像维护者。此类处理作为审计规则的必要例外，不为保留 Git 历史而继续暴露敏感内容；处理记录也不得复述泄露信息。

## 5. 静态发布、运行时与可迁移性

### 5.1 数据流与仓库职责

目标数据流：

```text
GitHub Issue／PR → 校验与人工审核 → 正式源数据及图片
                                      ↓
              Actions：校验 → 构建 → 预算检查 → 静态发布
                                      ↓
             Udon：轻量目录 → 当前分区 → 墓碑文字 → 按需图片
```

主仓库保存墓碑源数据、规则、审核结论和资源映射；图片仓库可分片。建议的逻辑布局为 `entries/`、`schema/`、资源映射及后续 `.github/workflows/`，图片可在主仓库的 `images/` 或登记的独立图片仓库中。本阶段不创建这些目录或文件。

新增身份绑定、评审记录、额度账本与政策版本由社区源数据维护，Actions 处理经授权的变更并生成静态结果。Udon 不负责写账、发奖或证明当前访客是账本中的某个账号；内容可以公开阅读，不需要绑定登录才能参观。

**REQ-21：受控发布。** Actions 校验字段、ID／墓位唯一性、数量上限和资源完整性，检查图片，生成目录／分区／图片衍生物，统计预算后发布。任一必需检查失败不得激活候选版本。发布是从批准数据构建的导出，不直接将整个源仓库复制为 Pages 网站。

新增墓碑的接纳与额度结算必须一并校验；接纳后的部署失败仅重试发布，不重复扣次，也不自动退次再扣次。具体记账建议见 REQ-36、REQ-37。

**REQ-22：投稿安全边界。** 投稿内容与文件均视为不可信输入。投稿校验不得获得生产发布凭据、写权限或执行投稿者提供的脚本；发布仅从受信任的审核结果触发。工作流和构建程序的变更需独立审查，不允许通过内容投稿绕过权限边界。世界内不保存 GitHub 写入凭据。

### 5.2 运行时数据契约

**REQ-23：版本与资源寻址。** 运行时至少表达以下信息，具体字段名和编码在技术设计阶段确定：

| 信息 | 用途 |
| --- | --- |
| 协议版本 | 判断世界能否理解该数据格式。 |
| 发布版本 | 区分内容更新，检查目录、分区和图片映射是否兼容。 |
| 分区目录 | 表达可访问分区和必要概要，不包含完整故事或完整图片集。 |
| 稳定墓位与墓碑 ID | 将已批准内容绑定到正确位置。 |
| 预置资源槽位引用 | 从世界已上传的地址表中选取分区或图片资源，不把任意字符串当成下载 URL。 |
| 图片展示映射 | 将逻辑主图、头像、纪念图关联到独立图片或合图区域。 |

多仓库部署不假设原子完成。当前设计将一组墓碑详情与压缩像素放入同一二进制文件，按目录／区域预期修订验证后共同应用；拒绝旧包和错组，不再把独立图片请求仅凭JSON版本号拼接。具体协议见运行时计划；POC-04仍需确认实际SDK传输与版本行为，不能把同文件一致性当成全网即时最新。

**REQ-24：无需重传世界的边界。** 在预置容量、既有地址表和兼容协议内，新增、修改、撤下与换图无需重新上传世界。超出容量、增加未预置站点／地址、修改世界逻辑或引入不兼容协议时，允许更新世界。不能通过从 JSON 返回新 URL 或拼接版本参数来假定绕过 Udon 的地址限制。

### 5.3 浏览、对象池与缓存

**REQ-25：按需加载。** 世界不保存完整墓地数据库，只保留轻量目录、当前区域和有限缓存。优先呈现文字与占位，附近按需显示缩略图，主动查看时加载详情图片。图像下载慢不应阻止阅读已经取得的文字。

**REQ-26：稳定空间与独立交互。** 同一发布版本下，访客看到相同墓碑对应相同墓位。个人详情界面和加载状态相互独立，不因某人查看墓碑而切换其他人的界面。本地显示对象通过有界对象池复用，是否使用特定 SDK 池组件留待技术设计，不据此要求全局同步个人浏览状态。

**REQ-27：有界资源调度。** 应用自行管理有界请求队列、并发／节流与缓存，优先当前查看内容；快速移动时移除尚未提交的过期请求，已提交但失效的结果不得应用到复用后的墓碑对象。图片离开使用范围且不再被引用时释放纹理，不能仅隐藏物体。缓存、重试和队列不得随历史访问数量持续增长。

**REQ-28：可解释的失败。** 断网、超时、限流、数据损坏、图片缺失、协议不兼容、分片版本不一致均应提供明确占位或错误状态，不得错配内容。已知被隐藏／撤下的内容不得因失败回退而重新出现。保留旧内容的条件、刷新与重试周期通过 POC-04 定义；不承诺跨会话持久离线缓存，也不承诺立即清除所有在线客户端已有缓存。

### 5.4 多仓库预算与交接

**REQ-29：预算与维护成本可见。** 每次构建统计各站发布体积、图片数量、资源引用完整性和分片归属，并预留平台限额余量。根据访客数量与下载策略估计带宽，评估 Git 二进制历史增长、备份体积和维护工作量。多仓库是存储组织方式，不是规避平台配额或保证无限带宽的手段。

**REQ-30：可恢复与可接续维护。** 备份覆盖正式源数据、采用的图片资源、跨仓库映射、构建规则和世界工程交接资料。社区应能在另一个 GitHub 项目重建静态产物；内容和图片须记录允许保存、展示、必要处理和社区接续维护的授权范围，不能仅因仓库公开就视为可任意再利用。

Fork／Mirror 数据不等于自动获得 VRChat 世界发布权限。世界工程及其素材的可交接性、VRChat 账号／世界权限、既有下载域名控制权分别检查；新维护者可能需要发布新世界或更新地址表。首版不承诺任意镜像都能被旧世界自动发现和切换。

## 6. 官方平台限制与可行性评估

以下来源核验于 **2026-10-02**，通过 Context7 查询官方文档并参考所列官方页面；不是对未来 SDK 版本的永久保证。

| 编号 | 已核验的平台限制 | 对本项目的影响 |
| --- | --- | --- |
| PLAT-01 | `VRCUrl(string)` 构造器仅能在编辑器阶段调用；运行时用户输入 URL 是另一种机制。[S1](https://creators.vrchat.com/worlds/udon/external-urls/) | 自动浏览必须使用预置地址表；不依赖访客逐个输入 URL 来补足容量。 |
| PLAT-02 | 文本下载每 5 秒一次，超限进入随机顺序队列；文档列出单次上限 100 MB、队列上限 1,000。[S2](https://creators.vrchat.com/worlds/udon/string-loading/) | 采用分区与应用队列；平台上限不是项目目标预算，不承诺即时完成全部文本加载。 |
| PLAT-03 | 图片下载每 5 秒一次，限制适用于整个场景；最大 2048×2048，输入／输出缓冲各最多 32 MB，队列最多 1,000；图片地址必须直达文件，禁止重定向。[S3](https://creators.vrchat.com/worlds/udon/image-loading/) | 多个下载组件不能增加限额；按需加载、缩略图／合图及主动释放是必要条件。 |
| PLAT-04 | `*.github.io` 同时列在文本与图片下载允许列表中；未列入的站点需要访客启用不可信 URL。[S2](https://creators.vrchat.com/worlds/udon/string-loading/) [S3](https://creators.vrchat.com/worlds/udon/image-loading/) | 默认采用直接的 Pages 地址；不把 GitHub Raw 地址或自定义域名视为自动获得同样许可。 |
| PLAT-05 | Pages 单站发布内容不超过 1 GB，月带宽软限制 100 GB；源仓库推荐不超过 1 GB。自定义 Actions 发布不受每小时 10 次构建的该项软限制，但仍受其他适用限制。[S4](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits) | 需跨仓库／站点预算；图片历史、构建次数、流量和部署成本仍要评估。 |
| PLAT-06 | Player API 的 Display Name 与登录用户名不同；`GetPlayerId` 返回玩家网络 ID。[S6](https://creators.vrchat.com/worlds/udon/players/) [S7](https://creators.vrchat.com/worlds/udon/players/getting-players/) | 不能将显示名或实例网络 ID 当作长期绑定和领取额度的控制权证明；当前核验的 API 文档未提供本项目可直接采用的账号控制权认证流程。 |
| PLAT-07 | Actions 提供并发控制，但默认等待任务可能被后续任务替换；配置排队也不等于应用层事务。[S8](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency) | 需要持久操作记录、幂等与基于最新状态的提交校验，不把一个 concurrency 配置当作防重复扣次的全部方案。 |

2026-10-03补充：生产图文传输改用StringDownloader原始字节和SDK已注册的纹理方法，PLAT-03保留为ImageDownloader背景限制，不再作为两通道调度依据。方法证据见 [SDK-EVIDENCE](../plans/SDK-EVIDENCE.md)，实际客户端验证尚未完成。

### 6.1 评估结论

**有条件可行，尚未完成技术验证。** GitHub 可承接协作、审核记录、构建与静态发布，Udon 可读取静态文本和图片；主要约束是预置地址规模、下载节流、图片内存、多站发布一致性及社区维护成本。

- “不自建服务器”不等于“没有托管服务、账号权限或运营责任”。
- “不重新上传世界”仅对已预置的兼容容量成立。
- “4,096 座”不等于“4,096 座同时实例化”，也不保证每座 7 张高清图。
- “多仓库存储”不消除世界地址表、Pages 流量和备份成本限制。
- “争议先隐藏”描述维护流程，不意味着能够立刻召回所有已下载内容。
- “保留历史”与“保护隐私”发生冲突时，必须允许受控的紧急清理。
- “绑定 VRChat”不等于识别唯一自然人；多 GitHub／VRChat 账号仍可被同一人控制。
- “去中心化”与“全球统一创建次数”存在取舍；首版建议社区自治、额度分域，而非构建跨社区共识系统。
- “参与评审有奖励”不能变成“赞成越多奖励越多”；质量核验与反串谋本身需要治理投入。

| AC-12 治理与发布安全 | REQ-18、REQ-19、REQ-20、REQ-22 | 未确认人物同意的投稿不能发布；紧急清理演练不复述敏感材料；恶意内容文件和工作流改动不能取得生产写权限或在特权流程执行。 |
| AC-13 玩家绑定 | REQ-10、REQ-32 | 区分关联玩家与成员绑定；显示名变化不改变额度主体；未核验声明不能显示为已核验，冒认、重复绑定和重放证明不能重复领取；不收集登录凭据。 |
| AC-14 初始额度 | REQ-33、REQ-36 | 依据确认后的资格规则，同一成员只发放 1 次初始额度；重试、改名、解绑／重绑和账号恢复不得自动再次发放。 |
| AC-15 评审奖励 | REQ-34、REQ-35、REQ-39 | 按确认的兑换比例奖励有效贡献；同一贡献重复提交、工作流重跑、自审或利益冲突不得领奖；有依据的拒绝意见与赞成意见使用相同质量标准。 |
| AC-16 并发与重试 | REQ-36、REQ-37 | 余额仅 1 时两条并发新建最多接纳一条；内容与扣次共同提交，重复回调、部署失败、重跑任务均不重复扣次或发奖。 |
| AC-17 更正与申诉 | REQ-17、REQ-38 | 奖励已消费后被撤销，有原因与复核记录，禁止进一步超支且不自动删除既有墓碑；恢复正确绑定不新建额度主体或重新发放。 |
| AC-18 复制与自治 | REQ-31、REQ-40 | 镜像恢复沿用原记录和去重标识；独立分叉明确社区身份、政策和承认的历史，跨社区余额不自动合并；维护者退出后可由授权继任者继续处理。 |
| AC-19 分享阅读 | REQ-41、REQ-44 | 已发布且部署成功的墓碑获得稳定分享链接；未登录、无 VRChat 账号的访客可阅读，失败部署不得报告链接已就绪；浏览不调用个人运营后端。 |
| AC-20 代建与非玩家对象 | REQ-18、REQ-42 | 覆盖为本人／他人、非 VRChat 人物、抽象对象建立墓碑的投稿；不虚构 VRChat 账号，不以代建绕过同意与授权。 |
| AC-21 正向循环 | REQ-33、REQ-34、REQ-43、REQ-44 | 分享页访客能够到达投稿与评审指南；邀请与点击不自动记为有效评审，合格评审按确认政策得奖；没有自建登录、数据库或常驻机器人。 |
| AC-22 分享撤下 | REQ-16、REQ-20、REQ-45 | 非公开状态同步排除世界与分享内容，受控正文、预览图、旧合图得到清理；保留通用不可用页，明确外部平台缓存边界，无项目级追踪脚本。 |
| AC-23 简单投稿与回执 | REQ-03、REQ-46、REQ-47 | 不熟悉Git的测试者完成填表、拖图、补充信息和跟踪审核；不写JSON／Fork；只在真实发布就绪后得到完整定位回执，失败状态清晰。 |
| AC-24 世界定位 | REQ-04、REQ-08、REQ-48 | 未绑定访客通过短码找到批准条目，先确认标题再指路／传送；不影响其他人。错误码、空槽、撤下、错世界与旧数据不误导或泄露隐藏内容。 |

## 8. 后续技术原型与开放前条件

| 编号 | 待验证内容 | 必须产出的结果 |
| --- | --- | --- |
| POC-01 | 4,096墓位与577预置地址 | 确认64区域、512组包映射和地址表的构建／运行开销，不依赖动态新URL。 |
| POC-02 | BC1图集与准确SDK调用链 | 在真实目标客户端从ResultBytes装载原始压缩纹理，验证方向、色彩、透明背景处理、七图映射和头显可读性。 |
| POC-03 | 满容量硬预算 | 构建512个最大组包，验证两数据分片与主站预算；源图和Git历史独立统计。 |
| POC-04 | 原子包、旧缓存与撤下 | 验证.bin字节保真、版本／长度／归属检查、跨站混合和迟到回调；不能以静态SDK注册或离线模型取代实机测试。 |
| POC-05 | 客户端性能与降级 | 确定对象池大小、队列／缓存上限、解码内存预算、文字显示与分区加载耗时、性能测试设备和测试时长。 |
| POC-06 | 无自建后端的 VRChat 绑定核验 | 验证人工查看账号控制证明的可行性、身份引用稳定性、冒认／重放／重绑处置及隐私成本；不假定存在官方 OAuth 或用 Udon 显示名冒充认证。 |
| POC-07 | 额度账本与安全结算 | 演练事件重放、重复奖励、并发消费、任务取消／重试、部署失败与补偿；证明无需自建常驻服务，并明确 GitHub 权限和串行结算责任。 |
| POC-08 | 评审激励与社区分叉 | 使用模拟案例检验兑换比例、互刷识别、反对意见公平性、评审任务不足和独立申诉；验证镜像恢复、分叉身份和本社区额度隔离。 |
| POC-09 | 静态分享、简单投稿和定位闭环 | 从分享阅读到GitHub表单、两种回执、世界输入定位码及有效评审再发布，验证新手完成率、无凭据前端和撤下清理。 |

上述参数尚未确定，属于下一阶段必须解决的问题；本需求文档不以任意数字替代验证。原型发现目标不可达时，记录证据并修订需求，不静默削减容量、画质或设备支持。

正式开放投稿前还必须明确：审核负责人及联系渠道、人物同意核验办法、紧急撤下职责、内容与图片授权范围、输入数值上限、GitHub 权限配置和备份责任。上述内容不得通过让投稿者在公共 Issue 提交私密证据来补足。

DEC-01～06已在本实施计划确认；真实额度机制开放前仍须实现POC-06～08、独立核验角色和账本测试，不能仅将开关置true冒充完成。

后续顺序：**需求定稿 → 下载与图片原型 → 技术设计 → 社区流程和世界实现 → 验收与开放**。
