## 1. 总体结论

**目标有条件可行，但旧需求不足以直接实现新机制。** 静态内容展示可以继续采用现有路线；身份控制权、奖励质量认定和额度结算需要新增一套可审计的社区流程。它们可以通过人工治理与按事件运行的 Actions 实现，不必自建常驻后端，但并不会因此自动变成无信任系统。

建议将首版明确为“无自建后端、可复制与分叉、社区自治的赛博墓地”，并把创建额度限定在各社区之内。此为架构边界建议，等待 DEC-06 确认，而非替用户将去中心化目标降级为已经确定的单一中心运营。

## 3. 平台证据与推论边界

- 官方 Player API 区分 Display Name 与登录用户名；Getting Players 将 `GetPlayerId` 描述为网络 ID。本轮据此要求不要将显示名或实例 ID 当作长期账号证明，并没有据此宣称官方提供本项目所需的绑定接口。[Player API](https://creators.vrchat.com/worlds/udon/players/) · [Getting Players](https://creators.vrchat.com/worlds/udon/players/getting-players/)
- GitHub Actions 有并发控制，但默认等待任务可能被替换；因此“只配置 concurrency 就完成额度事务”不成立。唯一操作记录、最新状态校验与可恢复结算是本项目的设计建议。[Actions 并发控制](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)
- 原有静态下载地址、图片频率、Pages 容量和撤下边界保持有效，详见主需求 PLAT-01～PLAT-05；本轮未重复执行下载或容量实测。
