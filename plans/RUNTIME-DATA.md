# Unity／Udon 运行时：分组原子图文包

更新：2026-10-03。替代旧的“每碑图片 URL＋像素版本标记”方案。能力依据见 [SDK-EVIDENCE.md](SDK-EVIDENCE.md)，比较见 [REDESIGN-2026-10-03.md](REDESIGN-2026-10-03.md)。尚未在 Unity／VRChat 客户端运行。

## 1. 核心决定

- 保留共享墓园、4,096 个固定墓位、64 区×64 槽；只显示附近内容。
- 每8座相邻墓碑组成一个图文组，共512组；组内最多56张逻辑图片打进一张2048×2048图集。
- 一个 `.bin` 文件同时包含JSON元数据和BC1／DXT1压缩像素，由VRCStringDownloader下载，再读取回调的 `IVRCStringDownload.ResultBytes`。生产墓碑图片不走VRCImageDownloader。
- 先验证整包修订及归属，再用 `Texture2D.LoadRawTextureData(byte[])` 装载纹理；不再合并两个独立HTTP响应中的文字与图片。
- 不用CPU逐像素绘制、像素版本标记、GPU回读、额外校验Shader、A/B轮换或有限不可变地址池。
- 首版限定Windows PC／PCVR；不将BC1路线自动承诺为Quest或任意图形后端可用。

“原子”仅指一次文件下载包含匹配的元数据和像素，不表示跨站部署有事务，也不代表返回内容一定是全网最新。

## 2. 分层数据与固定地址

| 层 | 数量 | 内容 | 本地保留 |
| --- | --- | --- | --- |
| `catalog.json` | 1 | 社区、协议、布局、发布序号、64区预期修订和数量 | 1份 |
| `regions/00.json` | 64 | 本区文字概要、位置、8个组包预期修订、可见性 | 最多3区 |
| `packs/000.bin` | 512 | 本组8槽批准详情、七图映射、BC1图集 | 最多2缓存组＋1暂存组 |

总计 **1＋64＋512＝577个预置VRCUrl**。根目录没有全库故事，区域概要没有像素。无图组使用小型纯元数据包，纹理长度为0，不创建空白大图。

真实站点在生产上传前配置，编辑器生成地址表。运行时只选择已有地址，不拼接路径或cache-busting参数。固定地址可反复更新；旧包通过包内版本拒绝，不靠清空CDN缓存。

## 3. 组包协议 v1

### 3.1 固定头：32字节，小端序

| 偏移 | 字节数 | 内容 |
| --- | --- | --- |
| 0 | 8 | ASCII魔数 `CCPACK01` |
| 8 | 4 | UTF-8 JSON长度：1～131,072 |
| 12 | 4 | 纹理长度：0或2,097,152 |
| 16 | 2 | 宽：无图0，有图2048 |
| 18 | 2 | 高：无图0，有图2048 |
| 20 | 1 | 编码：0无图、1 BC1/DXT1 |
| 21 | 1 | 保留，必须0 |
| 22 | 2 | mip数：无图0，有图1 |
| 24 | 8 | 保留，必须全0 |

其后是JSON，再后是原始BC1块数据；**不是把PNG、JPEG或完整DDS文件传给LoadRawTextureData**。最大包为32＋131072＋2097152＝2,228,256字节，约2.125MiB。先校验头、范围、格式、总长度，再分配纹理，拒绝截断、尾部多余数据和未知格式。

### 3.2 JSON语义

必须包含 `schema`、`community_id`、`layout_version`、`region`、`group`、`revision` 和固定8个位置的 `entries`。区域0～63、区内组0～7，全局包索引为 `region*8+group`。

每个公开条目有墓碑ID、稳定槽位、条目修订、批准详情和七图有无标志；未公开位置为null，不保留隐藏姓名或正文。槽位为 `group*8+组内位置`，与区域概要中的ID和位置一致。根目录声明区域修订，区域概要声明包修订，不按下载先后猜版本。

构建来源可作审计，但不是“所有分区必须与最新全局发布号相同”的条件。只有变化的区域和组需要重建；总JSON预算含故事及所有嵌套字段。

## 4. 已核对的Udon调用链

1. 根目录→当前区域概要，先显示批准文字和占位。
2. 靠近或打开详情时请求所属组包，同组8座共用一次下载。
3. 回调仅取一次 `ResultBytes`；不读取二进制响应的 `Result` 字符串，不重复触发副本分配。
4. 校验固定头、总长度、社区／协议／布局／组ID／预期修订与条目映射，旧包直接拒绝。
5. `Encoding.UTF8.GetString(bytes, offset, count)` 只解码JSON，以VRCJson逐层检查类型与范围。
6. 原生 `Array.Copy` 提取纹理块，创建 `Texture2D(2048,2048,TextureFormat.DXT1,false)`，调用 `LoadRawTextureData(byte[])` 和 `Apply(false,true)`。
7. 仍匹配当前请求及视图绑定代数才应用；元数据与纹理一起换入。失效结果释放暂存资源。
8. 淘汰时解除材质引用并 `UnityEngine.Object.Destroy(texture)`；新路线没有IVRCImageDownload，不能继续用其Dispose释放这些纹理。

以上方法的Graph注册与wrapper在官方SDK3.10.5中已核对，不是由普通Unity API推测Udon支持。未发现运行时 `SystemInfo.SupportsTextureFormat` 的对应暴露证据，不让它成为读取前提；目标平台格式兼容通过环境验收确认。

不使用ImageConversion.LoadImage、普通HTTP库、后台线程、NativeArray泛型重载或运行时编码器。集成冒烟测试仍必需，静态暴露证据不等于已运行成功。

## 5. 一致性与新鲜度分开

区域概要要求修订B时：完整A包因JSON修订不符整包拒绝；完整B包的详情与像素一次获得，验证后一起应用；截断包拒绝；视图已换到其他墓碑时，迟到结果不应用。

若根目录和区域都暂时仍是A，最多显示内部一致的A快照，而不是把A图拼到B详情。接受新目录后，变化区旧正文、详情、图片引用和交互立即失效；新数据失败也不恢复旧内容。

保证依赖受信任生成器从同一批准快照造包和正常HTTP整文件传输，不防恶意发布维护者。构建端记录SHA-256用于部署核对，但不把未经验证的Udon哈希算法加入首版。

**一致性不等于新鲜度**：CDN仍可能返回旧目录或旧包，不能保证瞬时获知撤下。世界展示当前发布序号，回执展示所需序号；尚未同步时明确提示并节流刷新，而不是告诉用户投稿丢失。客户端已接受过的新序号不得被迟到的较旧目录回退。

## 6. 图集布局与画质

2048²分4列×2行，每碑一个512×1024条带：上半512²主图；下半分4个256²格，其中3格纪念图；剩余格分4个128²格，3格头像、1格留空。每格留2px边缘，实际主图最多508、纪念图252、头像124像素，等比填边不默认裁切。

七张逻辑图完整保留，但比旧的单碑大图分辨率低，这是明确的容量／清晰度取舍，不宣称世界内原图高清。BC1为有损RGB；透明图片在投稿预览中展示扁平化背景，审批与最终输出一致。头像、含字图片和实际头显可读性必须验收，不能静默降低到不可读。

离线编码采用Microsoft DirectXTex的texconv，构建前锁定发布版本和校验值，在GitHub托管Windows runner运行，不需要个人服务器或运行时编码器。基础命令形态为 `texconv -f BC1_UNORM -m 1 -ft dds -o build/dds atlas.png`；输入已严格为2048²，不依赖工具临时缩放布局。官方说明支持BC1输出和用`-m 1`禁用mip。[texconv官方文档](https://github.com/microsoft/DirectXTex/wiki/Texconv)

生成器解析DDS格式，而不是假定固定头长度；剥离容器后检查尺寸、单mip、格式和恰好2MiB数据。M1用角标与色阶图固定上下方向、UV及sRGB处理，记录最终参数，避免两次gamma转换；编码器支持格式不等于视觉参数已验收。

## 7. 容量上界

| 项目 | 设计值 |
| --- | --- |
| 墓位与逻辑图 | 4,096座，最多28,672张逻辑图片，512个组图集 |
| 地址 | 577个，不随日常修订消耗新URL槽 |
| 单纹理 | 2048²×4bit＝2MiB，无mipmap |
| 单组包 | ≤2,228,256字节 |
| 全部组包 | ≤1,088.015625MiB；纯纹理1GiB |
| 数据分片 | 2个Pages站，各256包，≤544.008MiB／站，低于700MiB工程预算 |
| 主站 | 分享、网页衍生图、根目录及64区概要，独立700MiB预算 |
| 图片GPU数据 | 2缓存＋1暂存＝6MiB纹理块，预留8MiB预算，不含驱动／材质管理开销 |
| CPU临时数据 | 响应副本、提取像素和解析临时值分开统计，项目可控工作集目标≤16MiB；SDK内部开销实测 |

主站网页图集每组≤1MiB共≤512MiB，HTML每页≤16KiB共≤64MiB，其余目录、样式、字体留余量并在构建时检查。源图及Git历史另计，不能把当前产物上界当作历史仓库永久上界。

满容量拓扑为1主站＋2数据站。小原型可只用测试站，生产首次上传前仍预置完整拓扑；未来扩容或换未预置站点需要更新世界。

## 8. 单通道调度与缓存

所有目录、区域和组包共享StringDownloader的每5秒一次限制，不能沿用旧的文本／图片两通道并行预算。起始发起间隔5.1秒，进行中最多1，待发最多8。

优先：安全目录刷新→主动定位区域→当前区概要→选中组包→近邻组。正常冷启动第三次请求约在10秒后发起，另加网络／解析时间；不承诺即进即有图。

只保留当前关注与一个近邻组，不自动加载一整区8组。缓存满时先释放无引用旧组再接收新组。ResultBytes大数组不逐字节循环；头部仅32字节，像素提取走原生复制。

每资源修订最多2次自动重试，退避10秒、30秒；耗尽等人工操作或修订变化，人工重试冷却120秒。多个一致性失败合并一次目录复核，不形成刷新风暴。应用超时不等于SDK网络取消，迟到请求状态独立跟踪。

## 9. 空间与Module设计

64个固定庭区通过步道和转角控制视线，避免同时必须加载四区。初始128本地墓碑外壳服务当前＋过渡区；地面、道路和必要碰撞保持静态，不随个人加载状态消失。

内容读取Module只对显示方提供请求区域、请求条目详情、释放详情的Interface；URL、包校验、旧版拒绝、纹理与缓存藏在Implementation中。生产Adapter用SDK，测试Adapter注入旧包／错误／乱序。布局和版本规则为in-process逻辑，真实网络与SDK形成外部Seam；这不要求Udon支持C# interface关键字或泛型注入框架。

## 10. 发布、撤下和到达

同一批准快照生成组包、概要和网站，先部署产物并检查，最后激活根目录。跨站混合期间安全占位，不报告全量成功；部署重试不重复结算额度。

目录初始每60秒错峰检查，主动刷新也节流；这是轮询周期，不是全网传播时限。撤下重建受影响组包并清理网页图、旧产物与预览；已下载副本和外部截图不保证召回。

定位码暂定 `12-34`，人类显示为第12区第34槽，两段范围01～64；内部索引减1，即region=11、slot=33。它不是身份凭据。世界先验证当前公开记录、显示标题供确认，再指路或传送到安全步道，不通过显示名判断“我的墓碑”。墓位暂不自动复用，政策决定前不让旧定位码指向新内容。
