## 1. 结论

**在“不依赖个人运营服务器、优先依赖 GitHub”的定义下，方案有条件可行。** 世界是所有人可参观的共享墓园，不是每位投稿者单独拥有一个世界。网站阅读、社区投稿、评审、分享和额度结算均可围绕 GitHub 组织，不需要自建常驻后端。

最新路线为**每8碑一个原子图文包**：文字元数据与BC1像素一次下载，固定地址从4,225减少为577。弃用像素版本标记／GPU回读研究；下一步验证已获SDK暴露证据的调用链，再投入完整美术。身份和奖励仍在世界外。

## 3. 本计划的边界

- 官方SDK仅临时检查，四GitHub仓库已创建；尚未安装Unity、上传世界或部署Pages。
- DEC-01～06已随实施计划确认，pilot-v1配置保存批准值，真实功能后续验证。
- 64 分区×64 墓位、128 个本地对象、图片预算等是**技术原型起点**，不是用户已确认的数值指标或平台保证。
- 一个主社区的共享世界是首版范围；多图片仓库只是存储分片，不自动成为多个独立社区。
- 首版墓位不自动复用已确认，4,096不是无限累计容量。
- 邀请不发奖、绑定可选已确认；真实奖励仍关闭。

## 4. 先后关系

```text
M0 环境与基线 → M1 高风险原型 → M2 灰盒墓园 → M3 浏览与交互
                      │                              │
                      └→ M4 GitHub 静态发布 ─────────┤
                               └→ M5 分享与治理试点 ─┤
                                                     ↓
                                       M6 全容量与性能 → M7 发布交接
```

M5政策已确认，真实奖励仍需完整实现与独立核验；M1 图片一致性失败时可以继续文字／交互实验，但不能把它当作图文完整首发。公开发布需要技术、内容授权、治理和维护交接四类条件同时满足。

已完成第二次重设计：保留GitHub静态主路线，采用可核验API的二进制图文包，给出地址／数据上界，并补齐投稿到定位闭环。旧缓存可能影响新鲜度，但不会把不同HTTP响应的图文强行混合；客户端原型仍未执行。

## 5. 如何使用本计划

按阶段创建任务，将编号、责任人、依赖、证据链接与结果记录到项目。任务默认未完成；后续测试记录建议归档到 `plans/evidence/`，本次不创建空证据或伪造通过结果。计划与需求冲突时，以已确认需求为准，记录变更再调整计划。
