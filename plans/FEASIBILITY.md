# 可行性评估：采用可核验的原子图文包

更新：2026-10-03，替代旧的图片标记原型路线。当前项目是需求、计划与一个离线模型验证脚本，没有Unity工程或客户端实测。

## 1. 结论

在“优先GitHub、不依赖个人运营服务器、Windows PC/PCVR、共享墓园”的约束下，推荐 **区域概要＋8碑原子图文包＋BC1纹理＋本地有界池**。关键调用已在官方SDK3.10.5注册中查到，不再依赖下载图片可读性、未知像素标记或GPU回读。

这解决了图文来自不同响应而难以校验的问题，并为4,096座给出固定地址与数据量上界。它不证明目标设备帧率、不会让CDN瞬时刷新，也不自动解决审核和奖励治理。

## 2. 证据层次

| 层次 | 本次结果 | 不能推出的结论 |
| --- | --- | --- |
| 官方文档 | StringDownloader可读原始字节；Unity可装载匹配格式的原始纹理数据，BC1为4bit/px | 不等于所有普通Unity API都可被Udon调用 |
| 官方SDK静态检查 | Graph与wrapper中核对8个必需方法，包SHA-256匹配官方索引 | 不等于Udon编译和实际客户端调用已经通过 |
| 离线模型 | 30项协议、版本、映射、布局、定位码和容量检查通过 | 不等于进行了真实网络传输、GPU显示或性能测试 |
| Unity／客户端 | 尚未执行 | 不报告4,096座实测完成或固定FPS保证 |

详细方法、官方包与符号见 [SDK-EVIDENCE.md](SDK-EVIDENCE.md)；模型可运行 `node plans/validation/atomic-pack-model.mjs`。

## 3. 官方平台事实及影响

| 事实 | 来源与影响 |
| --- | --- |
| VRCUrl字符串构造仅编辑器阶段可用 | [External URLs](https://creators.vrchat.com/worlds/udon/external-urls/)；运行时从577个预置地址选择，不能拼接新地址。 |
| StringDownloader每5秒一次，单次上限100MB，ResultBytes是原始字节副本 | [String Loading](https://creators.vrchat.com/worlds/udon/string-loading/)；所有正文与二进制图文包共享一条节流通道，单包≤约2.125MiB。 |
| `*.github.io`在文本下载允许列表内 | 同上；以Pages直链提供.bin，不要求用户开启不可信URL；原始字节保真仍需客户端集成测试。 |
| LoadRawTextureData要求匹配尺寸、格式与mip数据 | [Unity 2022.3](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Texture2D.LoadRawTextureData.html)；不能传完整PNG/JPEG/DDS容器。 |
| DXT1/BC1为4bit/px的RGB压缩纹理 | [DXT1](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/TextureFormat.DXT1.html)；2048²单mip为2MiB，透明图需经预览确认背景。 |
| Apply可以释放CPU纹理副本 | [Apply](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Texture2D.Apply.html)；只读GPU纹理不需要继续保存大CPU副本，上传耗时仍测量。 |
| Pages单站≤1GB、月带宽软限制100GB | [Pages限制](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)；主站与两个数据分片分别有700MiB工程预算。 |
| ClientSim不能模拟全部客户端能力 | [ClientSim](https://creators.vrchat.com/worlds/clientsim/)；Windows桌面和PCVR真机验收必须保留。 |

工具链继续以已核验的Unity2022.3.22f1和Worlds SDK3.10.5为计划基线，实施前复核并锁定。当前主机是macOS ARM，Windows/PCVR设备、真实Pages地址与世界权限仍待实施时落实。

## 4. 满容量硬预算

| 项目 | 上界 |
| --- | --- |
| 墓位 | 64×64＝4,096 |
| 七图逻辑映射 | 4,096×7＝28,672，不等于独立下载数量 |
| 图文包 | 每8碑一包，512包 |
| 地址表 | 1根＋64区域＋512包＝577；旧方案4,225，减少约86.3% |
| 每包 | 32字节头＋≤128KiB元数据＋2MiBBC1像素 |
| 全部包 | ≤1,088.015625MiB |
| 数据站点 | 两站各256包，≤544.0078125MiB／站 |
| GPU图片块 | 最多2缓存＋1暂存，6MiB；管理开销另留余量 |
| 图文请求节流 | 每客户端最多每5.1秒发起一次；首次目录、区域、组包通常至少跨两个间隔 |

主站负责分享网页和网页衍生图，不直接给浏览器发送BC1包。每组网页JPEG预算≤1MiB、每页HTML≤16KiB，另留样式／目录／字体空间，按主站700MiB拒绝超限。源图历史仍可能增长，不能把当前站点产物预算等同于Git历史上界。

分组8适合相邻步行：一次下载获得8座的全部图。随机跨组只看一座时会多下载其他7座的图片，因此不是所有访问模式下都最省流量；分组1/4/8的比较与取舍见 [重设计报告](REDESIGN-2026-10-03.md)。

## 5. 可落地范围与剩余风险

| 项目 | 判断 |
| --- | --- |
| 共享墓园与固定定位 | 可设计为独立于身份的浏览能力，短码指向固定区／槽。 |
| 固定地址无限次日常更新 | 不需要消耗新URL版本槽；数据格式、站点和总容量保持兼容即可。不是保证永不更新世界。 |
| 错版本包拒绝 | 版本和像素同包，不需读图像像素；旧包、错组和迟到回调可在创建纹理前拒绝。 |
| 全网即时最新／撤下 | 不能保证；新目录已知后立即失效，CDN／旧会话可能仍处于旧快照。 |
| BC1图像质量 | 主图508、纪念252、头像124的明确折衷，需头显质量验收，不宣称高清原图。 |
| 提交、分享和奖励 | GitHub侧实施计划已批准pilot-v1资格与3:1兑换，功能仍待实现，不由Udon发奖。 |
| 非VRChat对象和代建 | 数据模型支持，人物同意／图片授权仍需审核。 |
| 无个人运营服务器 | 本架构满足，仍有GitHub和VRChat平台及维护者责任。 |
| 全球统一身份／跨Fork余额 | 不属于首版保证，不能用公开显示名补足。 |

## 7. 仍需用户或实施阶段确定

DEC-01～06已随实施计划确认，pilot-v1记录初始1次／3有效评审换1次／可选绑定。首版不自动复用墓位，4,096仍是有限容量；配置批准不代表功能完成。
