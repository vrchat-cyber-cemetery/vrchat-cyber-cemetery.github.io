# 计划完成后的再评估与优化结论

> 历史记录：2026-10-03已完成[新重设计](REDESIGN-2026-10-03.md)。本页关于每碑图片、ImageDownloader或图中版本标记的候选方案已被原子图文包替代；不得据本页旧数字实施。社区治理与反滥用结论继续适用。

日期：2026-10-02。评估顺序：完成六份计划初稿 → 两路独立只读复审 → 主代理合并修订 → 文档一致性检查。本轮是架构与计划评估，没有运行 Unity 原型。

## 1. 是不是最优解？

**原方向合理，但原始方案不能直接称为最优解。** “GitHub＋静态数据＋Udon”符合你的长期维护目标；然而如果照着“每张图分别下载、提前拆很多仓库、用显示名绑定、看到版本号就认为图片一致、按评论或邀请发奖励”实现，体验和治理都会出现问题。

优化后的建议是：

> GitHub 原生协作＋一个社区权威数据源＋按需扩展的图片静态分片＋固定分区和局部对象池＋有限固定 URL＋可验证的图文修订＋静态分享＋世界外有效评审记账。

这是当前约束下**优先实施的方案**，不是已经通过实测、可证明全局最优的系统。特别是图片版本验证和满容量成本，仍必须由 M1／M6 的结果决定。

## 2. 比较标准

优先级按用户目标排序：

1. 不依赖个人运营的常驻服务器，原维护者退出后能接续。
2. 隐私与内容正确性：不会错图、已知撤下不会复现、不能伪造绑定和奖励。
3. 共享墓园体验：位置稳定、可读、局部加载，不以全量卡顿换取表面容量。
4. 低门槛传播与真实贡献：网页可读、可代建、非玩家也能被纪念，不激励垃圾投稿。
5. 维护复杂度与成本：有限的仓库、可测的资源预算、简单的发布和恢复路径。

不以功能越多、实时性越强或“去中心化”术语越多作为更优的标准。

## 3. 候选路线比较

| 路线 | 优势 | 与目标冲突／代价 | 结论 |
| --- | --- | --- | --- |
| 全量加载全部墓碑、图片逐张下载 | 概念直观，数据结构简单。 | 活动对象和缓存随容量增长，图片节流使等待显著增加。 | 不采用。 |
| GitHub 静态发布＋有界分区浏览 | 无个人常驻后端、容易备份、可渐进验证；分享和治理可在同平台。 | 固定地址、缓存一致性、平台限额和人工审核仍需处理。 | 推荐，经过本轮修订后作为基线。 |
| 自建实时 API／数据库／机器人 | 可做动态身份与实时查询、统一写入服务。 | 重新引入个人运行服务、凭据和长期维护负担，违背已确认约束。 | 首版排除。 |
| 先实现全球身份与跨社区共同结算 | 可能覆盖更广的自治诉求。 | 协调和反滥用复杂度超出共享墓园首版，不能替代 GitHub／VRChat 本身依赖。 | 不把它作为首版前提。 |

## 4. 已合并回计划的优化

| 优化 | 原先风险 | 当前方案与收益 |
| --- | --- | --- |
| O-01 世界只读，协作写入在 GitHub | 把身份、审核和额度搬入 Udon 会引入不可验证身份与写入凭据。 | Unity 专注浏览；世界外核验和记账。边界可测试，维护更简单。 |
| O-02 先单社区、仓库按需增加 | 提前多社区／多仓库会带来权限、命名空间和发布编排负担。 | 一个权威社区数据与账本；一个测试站起步，实测后预置生产所需分片，不默认建 8 个站。 |
| O-03 图片合图＋无图跳过 | 7 张独立图造成至少约30秒的发起跨度，空白图也消耗限额。 | 区域缩略图＋单墓碑详情合图；无图内容用本地占位、跳过请求，功能种类仍保留。 |
| O-04 单套地址先行 | 默认 A／B 翻倍地址和清理成本，也不能彻底解决地址复用旧缓存。 | A／B只作比较实验；图片归属／版本可验证是硬门槛，不以方案名字代替证据。 |
| O-05 目录、分区、图片独立修订 | 一个局部编辑可能迫使全部分区跟着全局版本重写／下载。 | 根目录声明预期局部修订，构建来源只作审计；未变区域和图片复用。 |
| O-06 已知更新先失效 | 新目录已撤下，但新分区失败时仍保留旧正文／详情。 | 新目录发现变化即清空受影响视图并占位；失败不复活旧内容。 |
| O-07 真实内存和生命周期记账 | JPEG大小被误当显存；只清引用，下载句柄仍持有纹理。 | 规范化每通道8-bit，记录CPU/GPU/暂存，单图Dispose下载对象；数量上限服从字节预算。 |
| O-08 有限重试与目录复核合并 | 多个坏图可能不断触发下载／根目录刷新，挤占正常请求。 | 每资源有限退避、失败冷却、同根复核合并，人工重试也节流。 |
| O-09 分享和奖励分离 | 邀请数发奖推动拉人、垃圾投稿和互刷。 | 邀请帮助发现项目；额度只来自有效评审，赞成／反对均按质量判断。 |
| O-10 贡献记录不因满园丢失 | 容量不足时暂停全部结算，损害已贡献者信任。 | 停止新建接纳／消费，但保留已确认贡献；兑换暂停需公开原因和恢复条件。 |
| O-11 语义验收而非仅编号映射 | 编号出现了，却没测无写权限修改、恢复审核、独立申诉等具体行为。 | 新增普通成员维护与公平申诉测试，明确跨Fork隔离与恢复不重复发奖。 |
| O-12 分享撤下按真实控制边界验收 | 把一次源文件删除说成外部预览和所有缓存已消失。 | 分别验收当前产物、受控旧路径、新鲜请求、客户端已知修订与外部缓存告知；失败不报成功。 |

上述优化已写回运行时、Unity工作包、社区循环与测试计划，不只留在本评估报告中。

## 5. 政策层的优化建议，尚未替用户确认

- 建议一次额度对应一座墓碑；默认一次的目标保留，但 DEC-01 仍需明确。
- 建议 VRChat 绑定可选，GitHub 社区成员身份承担投稿与额度；被纪念对象无需 VRChat 账号已确认，不能将其误解为要求所有投稿者先绑定。
- 有效评审兑换比例通过封闭试点决定，3:1／1:1都不是已证明最优。评审可得性、独立核验成本和垃圾投稿比例比数字本身重要。
- 额度非货币、不可转让，不按邀请发奖；撤下退款、评审任务上限和独立复核人数仍须公开政策。
- 独立 Fork 是否接受本社区历史、是否互认额度，保持显式规则；不默认跨社区结算。
- 正式接纳前决定墓位是否能复用。如果不复用，4,096 是有限累计分配容量；如果复用，需要绑定代际和旧缓存安全验证。

这些政策待定不阻止合成数据的世界原型，也不能被原型代码硬编码成既定事实。

## 6. 下一轮何时重新评估

只有出现以下证据才改变核心方案，而不是为了“更先进”增加服务：

- 固定图片地址无法可靠拒绝错版本：停止完整图文热更新，提出明确限制或替代方案并确认需求，不能删除安全门槛。
- 4,225 地址表开销或图片成本超出预算：先调整分区／合图和存储分片，不引入运行时任意 URL 假能力。
- 图片合图使头像／纪念图不可读：比较增加有限详情页与预算的代价，不能静默牺牲内容表达。
- GitHub原生投稿对目标人群门槛过高：先改善指南和静态草稿生成，若仍要求匿名直接写入再另行评估托管服务；不偷建个人后端。
- 评审任务供给和质量无法支撑奖励：调整兑换与参与规则，先停新发奖并保留贡献记录，不转而奖励拉人。

完成这些原型与试点之前，最准确的结论是“**约束下更合适、风险已显式管理的候选方案**”，而不是已经保证长期最优。
